### Key RESEARCH.md patterns for this plan

**Pattern 2 (§Append-Only Movement Table):**
- `IMovementRepository` exposes ONLY `InsertAsync`, `GetByDocumentIdAsync`, `GetCurrentLocationAsync`
- NO `UpdateAsync`, NO `DeleteAsync` — compiler-enforced immutability (MOVE-04, D-08)
- `GetByDocumentIdAsync` JOINs Positions table to include position names
- `GetCurrentLocationAsync` uses `ORDER BY MovementDate DESC, Id DESC LIMIT 1`
- Movement date stored as `yyyy-MM-dd` TEXT (consistent with existing date format)

**Pattern 5 (§Movement Recording Dialog):**
- `RecordMovementViewModel` extends `ObservableValidator`
- Receives `Document` via `LoadAsync(document)` method
- Loads active positions via `IPositionService.GetActiveAsync()`
- On save: creates `RecordMovementDto`, calls `IMovementService.RecordMovementAsync(dto)`
- Sends `DocumentMovedMessage` via `WeakReferenceMessenger`
- After save: closes dialog (MainViewModel handles window lifecycle)

**D-09:** Current location = most recent movement's `to_position_id`, derived via SQL query
**D-07:** Movements recorded with FromPositionId (nullable), ToPositionId (required), Direction, MovementDate, Remarks
**D-08:** Movements append-only, immutable (no edit/delete)
**D-12:** Movement history displayed in chronological order (oldest first) in document detail panel

### Anti-patterns to AVOID (from RESEARCH.md §Anti-Patterns):
- ❌ Do NOT add `UpdateAsync` or `DeleteAsync` to IMovementRepository
- ❌ Do NOT add `CurrentLocation` or `CurrentPositionId` column to Documents table
- ❌ Do NOT hardcode position names in C# (no `enum OfficerPosition`, no `switch` on position name)
- ❌ Do NOT join Positions with `WHERE IsActive = 1` for movement history queries — historical movements must show deactivated position names
</interfaces>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Tampering | Movement data modification after creation | mitigate | IMovementRepository has ONLY InsertAsync — no UpdateAsync, no DeleteAsync. Compiler-enforced immutability (D-08, MOVE-04). UI has no edit/delete controls for movements |
| T-02-12 | Tampering | Invalid position ID in movement | mitigate | MovementService validates ToPositionId against active positions before INSERT. FK constraint on Movements table as defense-in-depth |
| T-02-13 | Tampering | SQL injection via remarks | mitigate | Dapper parameterized query. Remarks value bound via `@Remarks` parameter |
| T-02-14 | Spoofing | Movement recorded for wrong document | accept | Single-user desktop app. User selects document row before clicking Move. Document info displayed in dialog title for confirmation |
| T-02-15 | Repudiation | Movement deleted to hide document trail | mitigate | Append-only table — no DELETE path at repository or service level. Any "correction" must be a new inverse movement entry |
| T-02-16 | Information Disclosure | Movement history visible to unauthorized users | accept | Single-user desktop app — no multi-user access control. All data visible to the operator is by design |
| T-02-17 | Denial of Service | Excessive movement entries for a single document | accept | No practical DoS vector for single-user app. Movement table grows linearly with usage |
| T-02-18 | Tampering | Current location derived from tampered movement date | mitigate | Current location uses `ORDER BY MovementDate DESC, Id DESC LIMIT 1` — uses both date and insertion order. MovementDate validated as not future in service |

    6. DocumentService.cs — implement UpdateAsync per RESEARCH.md Pattern 4 exactly:
       a. Fetch existing document via `_repository.GetByIdAsync(documentId)` → throw `NotFoundException` if null
       b. Create `List<DocumentAudit>` for audit entries
       c. Helper method `void CheckAndAudit(string fieldName, string? oldVal, string? newVal)` — if not equal, add audit entry
       d. Compare each editable field:
          - CheckAndAudit("Sender", existing.Sender, dto.Sender)
          - CheckAndAudit("Recipient", existing.Recipient, dto.Recipient)
          - CheckAndAudit("Subject", existing.Subject, dto.Subject)
          - CheckAndAudit("OriginalFileNumber", existing.OriginalFileNumber, dto.OriginalFileNumber)
          - CheckAndAudit("Remarks", existing.Remarks, dto.Remarks)
          - CheckAndAudit("DocumentDate", existing.DocumentDate.ToString("yyyy-MM-dd"), dto.DocumentDate.ToString("yyyy-MM-dd"))
       e. If `audits.Count == 0`: return early — no changes to persist
       f. Begin transaction: `using var tx = _db.BeginTransaction()`
       g. Apply changes to existing entity (update its properties from DTO values, set UpdatedAt)
       h. Call `_repository.UpdateAsync(existing, tx)` within transaction
       i. Call `_repository.InsertAuditEntryAsync(audit, tx)` for each audit entry within SAME transaction
       j. Commit transaction
       k. On any exception: rollback transaction, rethrow
       IMPORTANT: Direction (Incoming/Outgoing) is NOT editable after creation. The DTO's Direction field is ignored during update — do NOT write an audit entry for Direction changes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Edit form → DocumentService.UpdateAsync | DTO passes modified field values; service compares against existing record |
| UpdateAsync → SQLite | Document UPDATE + multiple audit INSERTs must be atomic |
| Audit trail → UI | Read-only display — user cannot modify audit entries |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Tampering | Audit trail entries modified post-insert | mitigate | DocumentAudit table has no UPDATE/DELETE repository methods. DataGrid is ReadOnly. DB-level: no DELETE grant |
| T-01-12 | Tampering | Document update succeeds but audit entries fail | mitigate | Both in single `IDbTransaction` — rollback restores previous state. Atomic at DB level |
| T-01-13 | Tampering | Direction changed during edit | mitigate | Direction field excluded from CheckAndAudit. UI toggle locked in edit mode. Direction column NOT in UPDATE SQL |
| T-01-14 | Spoofing | User edits wrong document (opens doc A, edits thinking it's doc B) | accept | UI displays document ID and tracking number in edit header. User verifies before saving. Risk accepted for single-user desktop |
| T-01-15 | Tampering | Concurrent edit of same document (theoretical — single user) | accept | Single-user app. WPF runs on one dispatcher. No concurrent modification risk |
| T-01-16 | Information Disclosure | Old values visible in audit trail | accept | Audit trail is a FEATURE, not a bug. D-07 explicitly requires displaying old/new values. This is the intended behavior |
</threat_model>

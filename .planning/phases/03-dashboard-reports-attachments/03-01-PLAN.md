Implement in DocumentRepository using Dapper QueryAsync with parameterized SQL. Use the JOIN pattern from RESEARCH.md Pitfall 4 (ROW_NUMBER() OVER (PARTITION BY DocumentId ORDER BY MovementDate DESC, Id DESC) = 1 subquery). **DashboardViewModel:**

Constructor params: IDocumentRepository (injected directly — no service layer needed per RESEARCH.md architecture map), IServiceProvider (for resolving MainViewModel at navigation time).

Three ObservableCollection properties, all populated on load:
- `PendingByOfficer` (ObservableCollection<OfficerPendingCountDto>) — populated from GetPendingByOfficerAsync
- `RecentDocuments` (ObservableCollection<Document>) — populated from GetRecentAsync(7)
- `OverdueDocuments` (ObservableCollection<Document>) — populated from GetOverdueAsync(7)

Computed properties:
- `bool HasPending` → PendingByOfficer.Count > 0
- `bool HasRecent` → RecentDocuments.Count > 0
- `bool HasOverdue` → OverdueDocuments.Count > 0
- `int TotalPending` → sum of all PendingByOfficer.DocumentCount

Commands:
- `RefreshCommand` (RelayCommand, async) — reloads all three collections. Called on construction (auto-load).
- `NavigateToOfficerCommand(OfficerPendingCountDto)` — per D-03: resolves SearchViewModel via IServiceProvider, sets SearchSenderRecipient to the officer name, executes SearchCommand, then switches to the Documents tab. Uses WeakReferenceMessenger to send a `SwitchToDocumentsTabMessage` that MainViewModel receives.
- `OpenDocumentCommand(Document)` — per D-03: uses IServiceProvider to resolve and show DocumentDetailWindow (same pattern as MainViewModel.OpenDocumentDetailAsync).

Subscribe to WeakReferenceMessenger for DocumentRegisteredMessage and DocumentMovedMessage → auto-refresh.
